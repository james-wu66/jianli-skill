# 简历定制器（skill 版）

## 这个 skill 交付什么

用户自己的信息 + 用户自己简历的版式 + 目标岗位 JD → **一份按这个岗位改过的 Word（版式一个像素不动）+ 一份匹配报告**。

两条不可动摇的分工：

- **你（宿主 Agent）负责判断**：读事实清单、判岗位方向、挑选与改写要点、决定哪个文字节点放什么内容。
- **脚本负责确定性**：校验下标、按容器分套、原地替换文字、读写档案、补齐保底。这些一律不许你自己在脑子里做。

## 目录与命令

skill 根目录记作 `<SKILL>`（本仓库里是 `C:\Hermes 简历skill\skilldizi`），四个 CLI 在 `<SKILL>/scripts/cli/`。

数据和代码的对应关系由 `scripts/paths.py` 决定，优先级：环境变量 `RESUME_DATA_DIR` →
`scripts/data_root.txt`（一行绝对路径）→ **从 scripts/ 往上找第一个同时含 `profiles/` 和
`assets/templates/` 的目录**。在 `<SKILL>` 里直接用默认即可，数据就是 `<SKILL>/profiles` 和
`<SKILL>/assets/templates`。

⚠️ 本项目还有第二个壳（网页版 `app.py`，数据根是 `C:\Hermes 简历skill`）。**两边档案不自动同步**，
改完档案要说明"另一份要不要一起改"。

```
# 1) 把当前档案渲染成三段文本：事实清单 / 个人红线 / 评分短板
python scripts/cli/facts.py --out 素材.txt

# 2) 把一份简历摊成文字节点清单（下标|结构|文字）
python scripts/cli/dump_nodes.py 我的简历.docx --out 节点清单.txt

# 3) 用映射 JSON 校验并落成专属模板包
python scripts/cli/apply_map.py 我的简历.docx --map 映射.json --name 我的简历

# 4) 结果 JSON → 引擎保底 → 在模板上原地换字出 Word
python scripts/cli/postprocess.py --result 结果.json
```

可选参数（都各有默认值，不填就走默认）：

- `facts.py`：`--profile 名字.json`（默认当前激活档案）
- `dump_nodes.py`：`--max-len 80`（每条文字截断长度）
- `apply_map.py`：`--pack user_ab12cd34`（留空自动生成 `user_xxxxxxxx`）
- `postprocess.py`：`--profile`、`--template 包名`（默认取档案里的 `template`）、
  `--out 路径`（默认 `<数据根>/output/<姓名>简历_<方向>_<月日_时分秒>.docx`）

控制台是 GBK 时，脚本输出里的中文会被降级；**要读中文内容就加 `--out` 落成 UTF-8 文件再读**，
不要凭乱码猜。

## 主流程 A：用户第一次用（还没有档案或没有自己的模板包）

1. 让用户给一份**他自己的 `.docx` 简历**（PDF 吃不了，本项目没有 OCR，也不做配色重画）。
2. `dump_nodes.py` 导出文字节点清单，读它。
3. 从节点清单里认出**个人信息**，整理成档案 JSON 写进 `<SKILL>/profiles/<姓名>.json`，
   并把 `<SKILL>/profiles/active.txt` 指向它。字段结构照抄 `profiles/示例-张三.json`。
   **铁律：只提取真实存在的内容，拿不准的留空。** 档案里的 `modules[].angles`
   （按岗位方向准备的表述）**不可重建**，覆盖写之前先跟用户确认。
4. 按下面"版式映射"规则产出映射 JSON，走 `apply_map.py` 落成专属模板包。
5. 把 `apply_map.py` 报的 `missing` / `absent` / `counts` **念回给用户核对**（见那一节）。

## 主流程 B：日常定制（用户贴 JD 要简历）

1. `facts.py` 拿到**模板槽位数**（项目要点几行、技能几行）和三份文本：事实清单、个人红线、
   评分短板。**这是唯一信息源**，产出的条数必须等于它报的槽位数。
2. 读 JD，判 `fit` 方向。
3. 产出结果 JSON（结构见"输出契约"）。
4. `postprocess.py` 落 Word。脚本会替你补两件事：**技术栈按方向保底**、
   **缺字段用档案素材补齐**。它只补档案里真有的东西，不会替你编。
5. 报告落盘（见最后一节）。
6. 用一段话告诉用户：文件在哪、匹配分多少、缺哪几条、这次改了什么。

## 输出契约（结果 JSON）

`postprocess.py` 吃的就是这份。允许被 ``` 代码块包裹，也允许被截断——解析器会尽力恢复。

```
{
  "objective": "定制后的求职意向一句话，20字内",
  "fit": "岗位方向，按 JD 实际判断（前端/后端/全栈/AI应用/数据/算法/测试/运维/其他）",
  "project_title": "项目名称（取档案里最相关的项目）",
  "project_role": "本项目里对应的岗位角色，如 前端开发 / 后端开发",
  "project_points": ["●【核心】模块名：内容，45~90个汉字", "...条数 = 模板项目区行数"],
  "tech_stack": ["只放与该岗位方向相关的技术，4~6 项"],
  "skill_lines": ["●分组名：内容，40~80个汉字", "...条数 = 模板技能区行数，不含证书"],
  "project_links": {"github": "...", "demo": "..."},
  "match": {"score": 70, "recommend": "值得投/可以投/建议不投",
            "summary": "一句总评，30字内",
            "requirements": [{"item": "JD 要求点", "status": "matched/partial/missing",
                              "note": "差距说明，20字内"}]},
  "rewrite_notes": "本次改了什么，25字内"
}
```

## 任务一：把事实清单针对这份 JD 重新组织

- 全局硬规则，任何用户都关不掉：
  - **G1** 不得新增用户事实清单里没有的技能、项目、实习经历、奖项、工具。
  - **G2** 不得虚构任何实习经历、公司经历或工作内容。
  - **G3** 不要把证书/获奖写进技能清单——证书由系统单独写入简历的证书栏，写了会重复。
- 个人表述红线与技能标签黑白名单**只存在于 `facts.py` 输出的第二段**（来自
  `profile.rules`）。**绝对不要把某个人的红线抄进本文件或抄给别的用户。**
- `project_points` **条数 = 模板项目区的行数**（`facts.py` 第一行会告诉你"项目要点 N 行 ｜ 技能 M 行"，
  那个 N 就是条数，**不是固定 6 条**）。每条「●模块名：内容」，最核心的 2 条加【核心】；按与 JD 的相关度
  排序，优先用档案里**与该岗位同名的那条角度**的表述；长度跟事实清单里那句原话差不多，
  **不要为凑字数扩写**。
- `skill_lines` **条数 = 模板技能区的行数**（同上，不是固定 5 条），每条「●分组名：内容」，按与 JD 的
  相关度排序；不相关的分组可以改成相关角度，但不得编造。
- 条数**多了会被截掉、少了会在 Word 里留空行**，两边都不许发生：宁可回到事实清单里再找一条真实角度补上，
  也不要编，也不要交一份缺条的。
- `tech_stack` 极其重要：**只挑与该方向直接相关的 4~6 项**。
  - 投后端 → 只留 Python/Flask、数据库 SQL、RESTful API、Docker、CI/CD 这类；严禁出现
    JavaScript、HTML/CSS、PWA、前端动画。
  - 投前端 → 只留 HTML/CSS/JavaScript(ES6+)、SPA 架构、移动端响应式、前端动画这类；严禁出现
    数据库优化、鉴权方案、容器化部署。
  - 投 AI 应用 → 只留 LLM 集成、RAG、数据管道、Python 这类。
  - 投全栈 → 前端、后端**各留 2~3 项，两边都必须出现**。
  - **宁可少列，也绝对不要全列**——原样全列会被面试官认为没有专精方向。
- 求职意向：**JD 里写了明确职位名时直接照抄**（按需补"实习生"，20 字内），禁止换成档案里的
  可选意向；JD 没写职位名时，才从可选意向里选最贴的那个。

## 任务二：匹配分（禁止虚高）

- 从 JD 提取 4~8 个关键要求点，逐条判 matched / partial / missing。
- `facts.py` 第三段是这个用户的**真实短板**，必须参与扣分。
- JD 提到而事实清单里确实没有的东西（实习经历、团队协作、企业级项目、特定业务经验、
  高级框架、高并发/微服务），**判 missing 并如实扣分**，不要因为简历写得好就加分掩盖。
- 参考基准：4 条全 matched 通常 65~75；1 条 partial 扣 5~10；1 条 missing 扣 8~15。
  多数应届生对大厂岗位真实分在 40~70，打 85 以上必须有充分理由。
- **宁可诚实偏低**，也不要让用户拿着虚高分去投明显不适合的岗位浪费时间。

## 版式映射：哪个文字节点放什么内容

产出这个 JSON 后交给 `apply_map.py`，**由它校验并落包**（越界、一址多写、套数不一致会被拦下或修掉）。

```
{
  "fields": { "name": [...], "phone": [...], "email": [...], "birth": [...], "hukou": [...],
              "school": [...], "degree": [...], "major": [...], "courses": [...], "ethnic": [...] },
  "edu_line": { "nodes": [...], "format": "{period}<原样保留间隔>{school}" },
  "slots": {
    "objective": { "nodes": [[a, b], ...] },
    "proj_title": { "nodes": [...] }, "proj_period": { "nodes": [...] },
    "modules": { "nodes": [该区域全部下标，扁平列表] },
    "skills":  { "nodes": [该区域全部下标，扁平列表] },
    "tech": { "nodes": [...], "prefix": "技术栈：" },
    "github_url": { "nodes": [...], "label_nodes": [...] },
    "demo_url":   { "nodes": [...], "label_nodes": [...] }
  },
  "cert_text": { "nodes": [...], "bullet_nodes": [...], "label_nodes": [...], "clear_nodes": [[...]] }
}
```

判定规则，六条，一条都别改：

1. `fields` 是基本信息。标签和值拆在两个节点时**只列值节点**；同一个节点里就列该节点。
2. `modules`=项目要点（每条要点一个节点）、`skills`=技能条目（每条一个节点）、
   `tech`=技术栈汇总行、`objective`=求职意向、`proj_title`=项目标题行、
   `proj_period`=项目时间、`cert_text`=证书行、`github_url`/`demo_url`=链接 URL 节点。
3. **同一处内容常常存了两份**（一份在 VML 形状、一份在 Word 绘图，结构标记分别是 V 和 D）。
   处理方式分两种，别搞混：
   - `objective` 要按"同一句话的两个副本"分组，如 `[[52,53],[54,55]]`；
   - `modules` / `skills` **只给一个扁平列表**，把这个区域全部下标列上就行。
     分组由引擎按下标所在容器自动完成。**你不要自己按"每条一套"或"每份一套"去嵌套**——
     那种分法会被判为映射不可信；实测有过把它当成 10 套×2 条，结果同一句话被写进
     20 个位置、盖掉了简历其他区域。
     单值区域（`proj_title`/`proj_period`/`tech`/`github_url`/`demo_url`）同样给扁平列表，
     给嵌套会直接 TypeError。
4. **宁缺勿错**：拿不准的节点宁可不映射（整个键省略），引擎会保留原样。
   **严禁把同一个下标列进两个不同区域。**
5. **行级区域只列每段的 F 节点。** Word 常把肉眼看到的一句话拆成好几个节点（引号、
   字体切换、拼写检查标记都会切）——9/22 那份实测 140 个文字节点其实只有 66 个段落，
   一条项目要点最多占 9 个 run。清单里标 `F` 的就是"该段第一个有文字的节点"。
   `modules`/`skills`/`proj_title`/`proj_period`/`tech` 只列 F 那些，**同段其余碎片不用你管，
   导出器会自动清空**。把整段的 run 全列进来，条数就会变成 run 数、一句话被摊成好几行。
   `modules`（项目要点）和 `skills`（技能条目）就是这两块里"一条一句"的整句条目节点，
   【不要靠开头有没有 ● 来认】。分点符号可能是 ● / · / • / - / ►，也可能什么都没有
   （结构标记带 N 的就是 Word 自动项目符号，符号不在文字里）。
   正确判据是：同属一个区域、句式长度相近、连续排列的若干完整句子。
   区域靠上下文中「项目经历」「专业技能」这类小标题，以及它们所在同一个形状/同一容器
   来确定。孤立的符号节点、空节点、纯分隔符（如「/」）不算条目，不要列进去。
   同一项目里「●技术栈：…」这种汇总行属于 `tech`，不要算进 `modules`。
   `cert_text` 只列证书正文所在的节点（每套一个），同行拆出来的碎片（「证书：」标签、
   「/」分隔符、另一段正文）列入 `clear_nodes`。
6. 只输出 JSON，不要 markdown 包裹、不要解释。

### 映射必须让用户核对一次

`apply_map.py` 会回 `counts`（每个区域认出几处）、`samples`（每个区域前两次的实际文字）、
`missing`、`absent`。**把关键区逐行念给用户**：求职意向、项目要点、专业技能、技术栈。

- `missing` = 简历里**有这块标题但没认出来** → 请用户指出该区域的下标，重跑一次 `apply_map.py`。
- `absent` = 这份简历**本来就没有这块** → 如实说明"生成时这部分保持你的原文不动"，不要报警。
- `counts` 里 `modules`/`skills` 是**含双份**的（比如 6+6=12），别当成"认出 12 条要点"念出去。
- 状态是 `fallback` = 映射整体不可用，脚本没落包；按它报的原因改下标再来。

历史上这一步全自动、没人核对过，模型猜错就**静默不改**，用户拿到的是"看着正常但没定制过"的简历。
所以这一问不能省。

## 匹配报告落盘（网页版从来没做到的那半条需求）

`postprocess.py` 会把 `score` / `recommend` / `requirements` / `summary` / `rewrite_notes`
原样回给你。**生成 Word 之后，再落一份文本报告文件**（与 Word 同名同目录，扩展名 `.md`），内容：

1. 岗位方向判定（`fit`）与求职意向
2. 匹配分与值不值得投
3. `requirements` 逐条列 matched / partial / missing，缺的写清缺什么
4. 这次相对原简历改了什么（`rewrite_notes`）

理由：匹配分以前只存在于网页上，Word 里没有，投几十家之后回看"上周那家多少分、缺哪条"翻不到。

## 别做这些

- 不要用 `python-docx` 的 `doc.paragraphs` 去读或改简历——这类简历内容全在文本框
  （`w:txbxContent`）里，段落 API 读到的是空段落。**所有节点操作一律走 CLI。**
- 不要手改 `assets/templates/*/template.json`。要改映射就走 `apply_map.py`，校验器只认它。
- 不要为了"内容更像别人简历"而重画版式或改配色；本项目的版式保持是**结构上**不动节点换来的。
- 不要做自动填网申表、不解析 PDF、不接在线服务。
- 用户说"模板不要改变"就是别动版式和配色；说"不需要改那么多东西"就是精准小改，别顺手重构。

## 已知边界

- 简历里没有项目经历（实测见过这种应届简历）就没有东西可改写，这是**产品边界**，
  要如实告诉用户，不是 bug。
- 跨版式映射的可靠性只在**一份版式**上验证过（就是内置 `classic_blue`）。换一份别人设计的
  简历时，务必逐项核对映射结果并向用户报告。
- 生成结果不落 Word 之外的一切东西都在 `output/`，那里文件名含真实姓名，**不要提交进 git**。
